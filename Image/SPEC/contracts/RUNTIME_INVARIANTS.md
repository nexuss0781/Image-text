# Image VISION Runtime Cross-Field Invariants

**Status:** P2 consistency/adversarial review is complete under the two-party model recorded in [`../P2_REVIEW_RECORD.md`](../P2_REVIEW_RECORD.md). Phase 3 assigned clause IDs `RI-SS.NN` and mapped every numbered clause to executable case definitions in [`../TRACEABILITY.md`](../TRACEABILITY.md); the package checker verifies the mapping. These remain draft invariants, not implementation evidence or production approval. Field ownership and shapes are summarized in [`OBSERVATION_FIELDS.md`](OBSERVATION_FIELDS.md); stable error meanings are in [`ERROR_CATALOG.md`](ERROR_CATALOG.md); version and migration behavior is in [`COMPATIBILITY_POLICY.md`](COMPATIBILITY_POLICY.md).

JSON Schema validates local structure. The following rules require checked runtime logic and dedicated tests. Schema validity alone is not profile approval, reference resolution, proof of complexity, or implementation conformance.

## 1. Exact versions, profile binding, and admission

1. A producer emits only a schema/profile/error version supported by the receiving contract. The profile binds exact `profile_schema`, `observation_schema`, and `error_schema` versions. A receiver does not infer compatibility from a numeric version comparison or silently upgrade/downgrade a record. An unsupported exact version returns `UNSUPPORTED_VERSION`.
2. Unknown fields, enum values, content kinds, transform operations, feature IDs, tokenizer/vocabulary IDs, profile capabilities, payload schemes, and error codes reject. JSON parsers also reject duplicate object member names and non-finite values, including exponent overflow; no parser may ignore ambiguous data or silently supply a default. `additionalProperties: false` applies at each record object.
3. The pair `(profile_id, profile_version)` is immutable and is bound to the exact profile hash and contract versions. A selected profile and its observation/provenance versions must agree. `fixture_only` cannot be activated in production; `proposal` cannot be activated at all. An `approved` status is accepted only when a separate authorized approval record resolves and matches the exact profile bytes/hash, owner decisions, permitted workload/target and capabilities. The schema's `approval_record_id` alone is not authority.
4. Candidate limits or features are not production defaults. The general still-image record remains `status: proposal`; no runtime may infer approved access, retention, consumer, workload, or owner data from it.
5. Sample-range minimum and maximum must be finite and `minimum ≤ maximum`; supplied capture-time values are finite in the declared timebase. Values are validated against the declared range exactly; clamping, implicit normalization, channel reordering, and algorithm substitution are forbidden.
6. Each declared format/layout/channel-order/type combination has one explicit interpretation. Disabled or undeclared combinations reject. If strides are disabled, noncanonical strides reject; if enabled, row/plane stride and final byte offset must be sufficient and in bounds.
7. Before any allocation, indexing, pointer arithmetic, or narrowing conversion, compute width×height, channel/sample counts, strides/offsets, bytes, element counts, transform/intermediate/output counts, and aggregate work with checked arithmetic. Every result must fit the representation and every applicable profile cap. Actual decoded dimensions and layout are checked again after decode.
8. Dimensions are positive and satisfy width, height, pixel, channel, sample-type, exact byte-length, and stride limits. Passing individual width and height caps does not imply that every pair is within the pixel cap.
9. `quadratic_allowed`, `quadratic_complexity_allowed`, and `ml_libraries_frameworks_allowed` are false. Every enabled operator has a reviewed multivariable complexity model and explicit enforced bounds for every input-scaled count. `features.enabled` is an allowlist: an enabled feature may be omitted from an observation unless a separately specified profile requirement makes it mandatory; every emitted feature must be enabled. C++/Assembly and an audited mathematics-library boundary remain binding; an Assembly path has the same contract/reference as C++.
10. Resource ceilings are finite, representable, and enforceable. Zero is allowed only where the field explicitly represents disabled input or an empty queue/capability. A profile with mutually impossible limits cannot promise those combinations; request preflight rejects them before allocation.
11. Animation or multipage input is rejected unless enabled with an explicit frame-selection rule. Alpha compositing requires a declared in-range background; alpha preservation requires an output format that carries alpha. Unknown color transfer/orientation stays unknown unless an explicit transform is applied.

## 2. Payload-reference identity, integrity, and access

1. Every reference contains a scheme, immutable `reference_id`, `content_kind`, positive byte length in bytes, SHA-256 digest, `access_mode: read_only`, access-policy ID, and retention declaration. `reference_id` plus scheme identifies one immutable object version; a resolver must reject mutable aliases and must verify identity, declared length, digest, and authorization against the exact returned bytes.
2. A checksum establishes only that returned bytes match the digest recorded in the observation. It does not establish source authenticity, authorship, or capture time. A resolver must not use a reference to bypass access controls or retention policy.
3. Numerical payload kinds (decoded/canonical raster, feature values, visual-token IDs, validity masks, transform maps, uncertainty values) declare positive shape, dtype, layout, and byte order. The checked product of shape and element size equals the exact payload byte length. This draft admits tightly packed numeric payloads only; strides, padding, compression, or alternate encodings require a separately versioned payload contract.
4. Numeric values are finite where the dtype is floating point and satisfy their profile/operator-specific range. `uint8` uses `byte_order: not_applicable`; multi-byte numeric values use the declared little-endian encoding. Unknown dtype/layout/order rejects.
5. The reference `content_kind` must match the schema path: encoded image, decoded raster, canonical raster, feature values, visual-token IDs, validity mask, transform map, or uncertainty values. A generic reference cannot be reinterpreted as another content kind.
6. A raster reference's payload shape, dtype, layout, sample range, channel order and byte count agree with the profile and image fields. A feature/token/mask/transform/uncertainty reference agrees with its descriptor's shape, dtype, ordering, transform and exact bytes. Missing, stale, expired, unauthorized, mismatched or corrupt references return `REFERENCE_INVALID`; a transient resolver outage is `DEPENDENCY_UNAVAILABLE` and is distinct from an invalid object.
7. Access and retention values describe policy, not a promise that payload bytes are retained for a particular duration. The designated data/store authority controls actual policy. Test fixtures resolve only within their fixture set and cannot stand in for a production object store.

## 3. Source frames, transform serialization, and coordinate maps

1. `image.source_width` and `source_height` describe the validated decoded source raster. Canonical width and height are both required and describe the terminal transform output. The first transform source frame/dimensions equal the source image; every following transform's source frame/dimensions equal the preceding target; the final frame/dimensions equal `image.canonical_frame_id` and canonical dimensions.
2. A transform has a unique ID, exact transform version, operation, source and target frame IDs/dimensions, `mapping_type`, `mapping_direction: source_to_target`, and an explicit `invertible` declaration. `image.transform_id` resolves to the final transform in the ordered `transform_chain`. A composite operation is represented as an ordered chain, not an opaque `composite` mapping type.
3. Every coordinate uses the declared upper-left-origin, x-right/y-down pixel-center frame: the center of pixel `(column,row)` is `(column+0.5,row+0.5)`. A transform matrix acts on homogeneous source-center coordinates as `p_target ~ M · [x_source,y_source,1]^T`, with a row-major 3×3 matrix; homogeneous normalization is explicit. Matrix entries and intermediate values are finite.
4. An identity mapping has equal source/target dimensions and frame-coordinate meaning and is represented by an invertible identity map with its inverse. An affine transform supplies the matrix; if marked invertible it supplies a checked inverse matrix. A nonlinear transform supplies a bounded mapping payload; if marked invertible it supplies a checked inverse mapping. If not invertible, its valid domain is identified whenever a consumer needs source correspondence. Matrix and inverse-matrix entries and intermediate values must be finite. The runtime must verify inverse products/round trips against predeclared tolerances; the tolerance remains an open production input.
5. A crop, pad, resize, orientation, feature-grid or patch-grid mapping states its exact pixel-center rule, border/interpolation rule, output dimensions and valid domain. Merely naming the operation is insufficient. Unknown transform IDs, inconsistent dimensions/frames, nonfinite matrices, missing required mapping data or out-of-domain use rejects before publication.
6. A coordinate or pixel-policy change is versioned. No implicit resize, crop, padding, rotation, channel conversion, clipping, or alpha loss occurs. Degenerate shapes (one pixel, one row, one column) retain a well-defined coordinate frame; no neighboring coordinate is invented.

## 4. Features, quality indicators, and uncertainty

1. Each feature names an enabled profile operator and exact algorithm version, typed immutable payload, positive shape, dtype, units, coordinate transform, and optional channel names/mask. Shape product, channels, mask count, transform, and profile bounds agree. Features and visual-token IDs are modality-local evidence; neither is an ENCODER embedding or Cortex feature tensor.
2. Quality is descriptive measurement, not a probability, semantic correctness score, confidence, salience, or task acceptance claim. Every indicator has a registered name, method ID/version, finite value, units, and scope (`image`, `feature_region`, or `patch`). Spatial scopes resolve through an approved transform and affected-region reference. A `profile_gate` indicator may affect acceptance only if its threshold and policy are versioned and owner-approved; otherwise indicators are `descriptive_only`.
3. `accepted_degraded` means the record passed hard profile/integrity/resource checks while one or more explicitly reported degradation indicators apply. It does not mean semantically useful or safe for an unprovided task. Quality status cannot override a hard failure.
4. `uncertainty` is omitted only when the selected profile's uncertainty mode is `disabled`. If the profile enables `fixture_only_uncalibrated`, `uncalibrated_fallback`, or `calibrated` uncertainty, an accepted observation must include a valid uncertainty record; absence returns `UNCERTAINTY_UNAVAILABLE` rather than fabricating or silently omitting a value.
5. Each emitted uncertainty value is a finite float32 in `[0,1]`, with units `probability` and the unchanged ENCODER convention `0_is_highest_confidence_1_is_highest_uncertainty`. Image VISION passes values unchanged to ENCODER. It never writes precision, attention weights, emotion gains, policy values, or other sidecar/tensor semantics.
6. `calibration_status: calibrated` requires a registered immutable calibration profile, exact target event, method/version, calibration evidence and authorized held-out evaluation for the supported regime. Only this state supports a calibrated-probability claim for that named event. No threshold, event, evidence, or calibrated state is inferred from the number itself.
7. `uncalibrated_fallback` requires explicit profile approval and remains labeled uncalibrated. Its values remain bounded uncertainty scores under the Encoder convention; they are not relabeled as calibrated probabilities. If no approved fallback exists, reject with `UNCERTAINTY_UNAVAILABLE`.
8. `granularity: image` contains exactly one value with shape `[1]`. `feature_region` and `patch` contain one value per declared region/patch in the exact order and count, with alignment ID, coordinate transform, and validity mask matching the associated payloads. Masked-out positions are not interpreted downstream; any placeholder semantics must be explicitly profile-defined, not invented by Image VISION.
9. If uncertainty is present, top-level and provenance profile IDs match; its calibration state and any declared calibration-profile ID agree with the selected profile. Unknown regime, absent calibration, drift or missing evidence cannot be converted into an unjustifiably low uncertainty value.

## 5. Provenance and cross-field identity

1. Top-level `profile_id`, `provenance.profile_id`, and the resolved profile ID are identical. Request, observation, trace, producer, runtime, source, decoder, transform, feature, and uncertainty identities all refer to the same admitted execution and declared versions.
2. Caller-supplied source identity, stream/frame index and capture time are preserved exactly after finite/range validation. Missing metadata stays absent. Processing time is never substituted for capture time, and provenance never claims authenticity without external attestation.
3. `source_integrity_status: checksum_verified` means only that the referenced bytes were checked against their declared digest. `externally_attested` requires a resolvable `provenance.attestation_ref` of kind `provenance_evidence` and authorized verifier; it is not set from the checksum alone.
4. An observation carries references and bounded metadata, not arbitrarily embedded image bytes. At least one image or feature evidence reference must be present. Optional capabilities absent from the selected profile cannot appear in the observation. The current profile schema has no token-authorization field, so `visual_tokens` must reject until a separately versioned profile extension can authorize it.

## 6. Stable errors, retries, and publication atomicity

1. Every rejected request returns an error envelope with matching request/trace/profile identities, exact supported error version, stable catalog code, bounded non-sensitive message, retryability, and `state_changed: false`. The retryability policy in [`ERROR_CATALOG.md`](ERROR_CATALOG.md) is normative; error messages are never parsed for control flow.
2. `state_changed` is always false and no error response contains or publishes an observation, partial feature/token set, payload bytes, local path, private content, credentials, or unbounded caller text. Runtime message size is at most 512 UTF-8 bytes.
3. A complete observation is assembled privately and published once only after required stages, payload resolutions, profile/version checks, schema validation, cross-field checks, and integrity checks pass. Any failure discards the private candidate and request-local scratch/reference handles. Publication has no partial-success state.
4. Only transient `BACKPRESSURE` and positively identified transient `DEPENDENCY_UNAVAILABLE` may be retryable in this draft. `retry_after_ms` appears only when retryable and is a finite nonnegative integer. Retrying preserves the idempotency key, exact payload identities/checksums and selected profile version; retry attempts and delays are bounded. A different payload or profile is a new request.
5. Cancellation, deadline, resource rejection, store/decoder/transform/feature/uncertainty failure and telemetry failure cannot mutate persistent state. A telemetry failure after publication leaves the already-published observation byte-for-byte unchanged.

## 7. Bounded work, memory, and privacy

1. Aggregate live bytes include input ownership, decoded raster, transforms, feature maps, masks, uncertainty, output buffers, decoder scratch, queued requests, and concurrent requests. Each allocation is preflighted against the active profile; a request never exceeds a declared cap before rejection.
2. Work counters include all input-scaled loops and operations, including copies, conversion, sorting, indexing, hashing and serialization when those scan input-sized data. No operator may hide a quadratic or worse term under “overhead.” Every input-scaled count uses explicit variables and finite bounds; all computation remains subquadratic in each input-scaled population.
3. Active requests, queue, reorder window, telemetry events, labels and diagnostics have finite limits. Queue-full behavior is explicit `BACKPRESSURE`; Image VISION never silently sheds an accepted still-image request.
4. Telemetry is read-only and bounded. It may contain approved counts, durations and codes, not image bytes, pixels, private source paths/content, access credentials, or unbounded labels by default.
5. Cancellation/failure releases request-local resources under the declared lifecycle contract. Test evidence measures or accounts for simultaneous peak memory; average timing does not replace checked resource bounds.

## 8. ENCODER boundary

1. Image VISION emits an Image Observation and references only. It does not emit `TensorValue`, `X[B,S,F_in]`, an M2 request, or a direct Cortex call.
2. ENCODER owns token lookup/embedding, sequence ordering/alignment, `valid_mask`, and numeric tensor assembly. The mask uses ENCODER/M1's `true_is_valid` convention. Image VISION visual-token IDs, if a separately approved extension ever emits them, remain modality-local symbols and are not numeric M2 features.
3. ENCODER preserves source references, modality tags, position, optional caller-supplied time, spatial frame/units, and Image VISION uncertainty unchanged in its sidecar. The Image VISION uncertainty convention and units must remain exactly aligned with the approved ENCODER contract; any change requires a reviewed version change at both boundaries.
4. Cortex receives only the registered finite numeric tensor and approved ENCODER-owned sidecar. Raw image bytes/pixels, image feature payloads, token IDs, time, uncertainty and spatial metadata are not passed as Image VISION numeric feature values. This draft changes no Cortex file or schema.

## 9. Required conformance probes

**RI-09.01 — Required positive and negative case families.** The specification-package checker validates test-only records and selected structural/cross-field rules; it does not execute an Image VISION component or close the Phase 3 harness gate. The future case catalog must retain positive and negative cases for exact/unsupported versions, unknown fields/enums, profile-contract binding, approval evidence, payload resolver immutability/access/checksum/length/shape/type/content-kind, transform chain frames/dimensions/direction/inverse/domain, quality scope and acceptance ownership, uncertainty disabled/fallback/calibration/range/count/mask alignment, provenance mismatch, every error code and retryability, cancellation at every publication boundary, duplicate retries, budgets/privacy, and Observation→ENCODER/Cortex route assertions. Catalog definitions have `definition_status: defined` and an execution status of `not_run` or `blocked`; only an actual implementation run may report `pass` or `fail` with reviewed artifacts.
