## Roadmap rule

This roadmap sequences requirements, test oracles, component engineering, integration and release evidence. It does not authorize implementation merely by describing a phase. A phase starts only when its entry gate is accepted; a phase closes only when its outputs and evidence are reviewed and recorded. A blocked optional capability remains disabled rather than being approximated silently. Requirements on the implementation language/dependency set and subquadratic complexity apply to every phase, test path and optimized path.

## Cross-cutting engineering sequence

1. **Decision before code:** settle every value that would alter an API or numeric meaning; assign an accountable owner and rationale. Deferred choices stay visibly deferred and block only the dependent capability.
2. **Contract before implementation:** define shape, dtype, units, coordinate mapping, buffer lifetime, cancellation, error and complexity for an operation before code exists.
3. **Oracle before optimization:** approve analytic fixtures and independent expected results; add implementation only after expected outputs are fixed.
4. **Atomic outputs:** construct observations privately, validate all references and invariants, then publish once. Errors publish no observation.
5. **Reference parity:** every Assembly or alternate native path is checked against the approved C++ contract/reference. Both obey the same asymptotic work limit; there is no performance waiver for quadratic work.
6. **Measure named workloads:** benchmark input distributions, device, concurrency and budgets chosen by the consumer owner. Synthetic fixtures demonstrate mechanics, not production performance.
7. **Trace every claim:** map each requirement to contract fields, harness cases, raw evidence and release decision in [`TRACEABILITY.md`](TRACEABILITY.md).

## Conditional capability branches

- **Visual token IDs:** disabled until an owner selects a deterministic/custom tokenizer contract, vocabulary identity, patch traversal, invalid-region policy and ENCODER consumption contract. IDs never enter Cortex as raw values.
- **Calibration:** calibrated probability language is disabled until target event, dataset authority, held-out split, metrics and acceptance criteria are supplied. Otherwise use an approved, explicitly uncalibrated fallback or reject.
- **Frame streams/video:** only independent image processing of caller-identified frames is in the base path. Sampling, temporal association, optical flow, tracking, synchronization and clip reasoning need their own specifications.
- **Custom learning:** no external ML library/framework is allowed. Any from-scratch trainable method is still optional and must pass Learning authorization, data governance, task evaluation, stability, versioning, resource and complexity gates.
- **Assembly path:** architecture-specific Assembly is admitted only after a correct C++ operation exists and a measured bottleneck matters to the named workload. The portable contract/reference remains authoritative.

## Non-goals of this roadmap

The roadmap does not set a production image size, feature width, token vocabulary, codec list, deadline, memory cap, target SLO, uncertainty threshold, domain certification, algorithm vendor, compiler, or library brand. It does not migrate `src/Vision/IMAGE/` into this directory, edit `SPECS/VISION.md`, change Cortex, reuse the `image-text` prototype as implementation, or start an image component. Those omissions are intentional decision gates, not unfinished engineering claims.
